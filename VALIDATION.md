# Validation record

The application is a development build. These checks establish implementation behavior, not real-model image quality or a 16 GB VRAM guarantee.

## 0.1.9 fast full-caption training checks

On 2026-11-04, the complete automated suite passed **418 tests, with 6 skipped** on the local runtime and GPU. After adding checkpoint-time cache RAM release, the affected cache, long-caption and fast-training integration checks passed again (**44 tests**). Additional cache tests cover releasing only disposable RAM copies, encoder-free disk reloads, unchanged fixed samples, and unchanged posterior sampling streams.

The new fast profiles were exercised on independent temporary copies of two finalized images: a 1216×832 image with a **1,225-token** caption and a 1664×640 image with a **905-token** caption, counts including BOS/EOS. Both use complete-caption chunking. The stored conditioning tensors had **1,309 and 1,001 positions**, demonstrating 17 and 13 native CLIP windows rather than caption truncation. Source images, captions, model files, and captioning prompts were not modified.

Both tests used the canonical local SDXL Base 1.0 Diffusers files, BF16 UNet/text storage and forward, FP32 frozen VAE, GPU cache preparation, one deterministic cached latent per image, GPU saved activations, checkpointing, micro batch 1, accumulation 1, and explicit TF32 acceleration. LoRA used fused GPU AdamW at `1e-4`; full fine-tuning used paged 8-bit AdamW with the `130` binary override at `1e-6`. These test rates are independent of the user's preserved experiment rates.

- **LoRA:** two optimizer steps took approximately **0.75 and 0.50 seconds**, after about **3.11 seconds** of frozen-cache preparation. Sampled peak GPU use was **7,216 MiB**; observed worker swap was zero. A resumable checkpoint and complete Diffusers output were produced, and adapter B weights changed.
- **Full fine-tune:** the initial two steps took **2.52 and 2.72 seconds**, after about **2.70 seconds** of preparation. Sampled peak GPU use was **15,838 MiB** out of 16,303 MiB. Checkpoint saving took **14.93 seconds**, a complete Diffusers output was produced, and a UNet weight changed. The initial run sampled about **531 MiB** worker swap during final saving. The worker was then changed to release disposable frozen-cache RAM copies before checkpoint serialization; a repeated two-step run also completed with the same full conditioning lengths and **zero observed worker swap**. This repeat does not isolate the cache-release effect from filesystem and system-state variation.

The runs include only two images and two optimizer updates. They do not establish long-run convergence, quality equivalence, sustained throughput, or memory fit for every image in the 2,300-image dataset. GPU sampling can miss brief peaks; the full run remains close to the card's capacity. Process I/O remains substantial when writing full model and optimizer checkpoints, even when optimizer-step I/O is low. Packaging work overlapped some preparation/saving, so these are practical smoke-test timings, not controlled optimizer benchmarks. Logs and detailed reports are in ignored local `build/benchmark/` files; temporary model outputs and dataset copies were removed after verification.

The user's editable project was renamed from `Modeling` to `Photo-Realistic` in the home-folder application's `projects` directory. All **9,218** project files were hashed before and after: every draft/finalized image and caption, `project.json`, the finalized manifest, and `caption-prompts.json` remained byte-identical. Only 15 historical launch records had project path prefixes updated. Global captioning settings, experiment learning rates, duration, and seed were preserved while selecting the new training speed controls.

- Explicit-network-only downloader, revision pinning, content verification, resume, safe redirects, no-clobber completion, and canonical SDXL file selection.
- Native Qt UI workflow: all pages, import/edit/switch/reopen, caption recovery, actual finalization, tokenizer subprocess communication, and dictionary-unavailable behavior.
- Named-project defaults, saved workspace preferences, and matching dark file browsers.
- Expandable drafts with sealed in-project dataset revisions, project-contained launch records, confirmed purge boundaries, and resume after moving a project outside the application.
- Disk AdamW numerical comparison against ordinary torch AdamW, configuration checks, SDXL checkpoint key conversion, and actual tiny SDXL LoRA/full training.
- Disk AdamW fp32 accumulation, clipping and checkpoint resume compared against the baseline; CPU and GPU optimizer updates can differ slightly in rounding. Frozen-VAE posterior cache checks include fresh stochastic samples and trainable-VAE bypass.
- Phase-timing and device-UUID GPU-monitor tests, including unavailable-monitor behavior and parsing available RAM, system swap, and worker swap. A small GPU operation exercised CUDA event timing and local NVIDIA sampling; this does not establish peak memory or throughput for full SDXL.
- Tiny all-component training with checkpointing/accumulation, stopped and resumed execution, merged Diffusers reload, and bitwise equality of resumed versus uninterrupted resulting weights.
- Package runtime hashes, archive traversal/link rejection, pinned release enforcement, extracted Qt imports, SVG rendering, and bundled llama-server version check.
- Real Debian archive permission checks: every installed directory is traversable and the bundled caption server is executable by regular users.

## Reduced-precision and long-caption validation

- The real SDXL tokenizers and small CLIP/SDXL models have tests for 256, 512, and 1,024 content tokens. A 1,024-content-token test exercised 14 windows and sent all 1,078 positions to the tiny UNet; both encoders received gradients from the tail. Short-caption encoding matches the original single-window behavior. This is not a full-size 1,024-token hardware run.
- On the RTX 5080 Laptop GPU, a full BF16-weight/BF16-VAE staged run used two different Set-01 images (1216×832 and 832×1216), one with a 306-token caption. With a 0.5 PyTorch allocation fraction (approximately 8 GiB), batch 1, fp32 optimizer masters and disk AdamW, two optimizer steps completed in 203 and 464 seconds. The checkpoint saved in 100 seconds; all four components had changed weights and the Diffusers output completed. The highest app-telemetry sample was 7,898 MiB; sampled worker swap was zero. A late process I/O sample showed about 191 GiB read and 213 GiB written, not direct SSD wear. The preceding test with an fp32 VAE exceeded that allocation cap before the first update.
- With an uncapped GPU, fp16 model weights and forward with the default fp32 VAE completed two full all-component steps on distinct 832×1216 Set-01 images using CPU text encoders and CPU AdamW updates. Step times were 235.6 and 241.4 seconds; saving took 68.0 seconds. Sampled peak GPU use was 15,074 MiB; all four components changed and the Diffusers output completed. The fp32 VAE was loaded from an fp16 source variant, so converting it to fp32 did not restore the source precision.
- A separate uncapped bf16 model/forward test with the fp32 VAE and GPU text encoders completed the same two image steps in 180.7 and 185.3 seconds with CPU AdamW updates; saving took 64.4 seconds and all four components changed. Sampled GPU peak was 15,018 MiB, sampled worker swap was zero, and a late process I/O sample showed about 189 GiB read and 213 GiB written. Source VAE weights in this test were bf16. The placements differ, so these numbers cannot isolate the effect of model precision.
- Using the same two short-caption 832×1216 images and GPU-text placement, a bf16 full run with CUDA fp32-master updates completed its two steps in 155.1 and 160.1 seconds; checkpoint save took 87.2 seconds. All four components changed and the Diffusers output completed. Peak GPU memory was 15,134 MiB in independent sampling, and sampled worker swap was zero. A late process sample recorded about 195 GiB read and 187 GiB written. The otherwise similar CPU-update run took 180.7 and 185.3 seconds per step, so CUDA updates were about 14% faster in this short run; this is not a general speed guarantee.
- The matching uncapped fp16 GPU-text and CUDA-update run completed two steps in 169.8 and 198.7 seconds, with a 124.2-second checkpoint. All four components changed and the Diffusers output completed; independent peak GPU use was 15,134 MiB, sampled worker swap was zero, and a late process sample showed about 195 GiB read and 187 GiB written. The two-step bf16 run was faster in this comparison, but disk timing fluctuates and these measurements do not establish visual quality. Both used fp32 VAE computation loaded from their respective already-rounded source variants.
- After reusing unchanged staged UNet snapshots, the same bf16 GPU-text/CUDA-update configuration completed two full all-component steps in 132.6 and 148.8 seconds and saved its checkpoint in 68.0 seconds; all four components changed and Diffusers output completed. Instrumented process I/O showed the first bf16 UNet park wrote about 4.8 GiB, while its second park in the same step wrote zero additional bytes. Process-wide counters still included approximately 39 GiB of writes during each optimizer update, and I/O varies with page cache and workload. During final Diffusers export this run sampled up to 2,148 MiB worker swap, despite completing; do not treat these figures as a no-swap guarantee.
- An uncapped UNet-only bf16 full run with GPU-resident saved activations and fp32 gradients in RAM reached two different images in 73.5 and 73.8 seconds, with a sampled GPU peak of 6,882 MiB. However, it did not complete: the safety watchdog killed the worker during checkpointing when worker swap exceeded 3 GiB. This is a failed memory-fit test, not a successful training output. RAM gradients are now admitted more conservatively for reduced-precision full training, and unused RAM gradients are released before checkpoint serialization; those changes require their own measurements.
- A fully fp32-weight/fp32-compute, all-component run on the 16 GiB GPU with both text encoders on GPU, staged UNet, disk gradients and CUDA optimizer updates reached UNet forward/backward but ran out of VRAM during the first VAE backward, before an optimizer step. A 494 MiB allocation was requested with approximately 38 MiB free. This is not a speed result; another placement may fit.
- The fully fp32-weight/fp32-compute all-component run with CPU text encoders completed two optimizer steps in 146.8 and 148.8 seconds, but the watchdog stopped it during checkpointing when worker swap reached approximately 2.3 GiB and free system swap fell below 2 GiB. This is a failed complete-run test, not a finished output. A later retry used the bounded-memory checkpoint writer.
- With the bounded-memory Safetensors checkpoint writer and 512 MiB final Diffusers shard target, the same fully fp32-weight/fp32-compute, CPU-text all-component setup completed two steps in 135.4 and 170.2 seconds, saved a resumable checkpoint in 56.6 seconds, and produced Diffusers output with all four components changed. Sampled peak GPU use was 15,422 MiB and observed worker swap was zero; the last process sample recorded approximately 173 GiB read and 174 GiB written. Sampling can miss brief peaks. These timings are not a precision-only comparison with the GPU-text bf16 run.
- With the updated staging and checkpoint writers, a 0.5 allocator-cap BF16 UNet/text/VAE run completed two distinct 832×1216 images in 244.1 and 225.2 seconds; checkpoint save took 101.0 seconds, all four components changed, and Diffusers output completed. A matched run with the new fp32 CPU text-encoder option completed in 150.7 and 181.9 seconds, saved in 87.5 seconds, and also changed all four components. The latter averaged about 29% faster over these two steps, but uses different text-weight and conditioning precision. Both runs used bf16 VAE computation and a locally converted bf16 source, sampled peak GPU use of 7,866 MiB and no worker swap; sampled process I/O for the latter was approximately 179 GiB read and 206 GiB written near completion. This does not validate image quality or an actual 8 GiB GPU.
- With fp16 UNet/forward, fp32 CPU text, fp16 VAE, and the same 0.5 allocation cap, the full run stopped before its first update due to a non-finite diffusion loss. An isolated fp16 VAE encode on both test images produced non-finite posterior mean, log-variance, and sampled latents. This specific source VAE is unsuitable for fp16 computation on these images; use fp32/bf16 VAE computation or validate an appropriate fp16-safe VAE. No checkpoint was overwritten.
- An additional 0.5-cap run with fp16 UNet/forward, bf16 VAE, fp32 CPU text encoders and fp32-master Disk AdamW completed the same two images in 188.6 and 191.5 seconds, saved its checkpoint in 152.0 seconds, and produced Diffusers output with all four components changed. Peak sampled GPU use was 7,866 MiB with no worker swap observed; last sampled I/O was about 179 GiB read and 206 GiB written. Its source variant was fp16, including already-rounded source VAE and text weights.
- An explicit paged 8-bit AdamW UNet-only full run used the BF16 local source variant, fp32 VAE compute, CUDA 13.0 bitsandbytes 0.49.2 binary override with PyTorch CUDA 13.2, and the same two 832×1216 images. Two steps took 16.0 and 16.4 seconds, checkpoint save 19.7 seconds, and a Diffusers output completed. GPU use sampled up to 15,832 MiB; one repeat sampled up to about 2.2 GiB worker swap at save, showing tight memory headroom. Its direct BF16-weight updates and quantized moments are a different numerical method from fp32-master Disk AdamW; no claim of equal quality or long-run stability follows.
- The 8-bit mode was also stopped after step 1 and resumed for step 2 at full SDXL size; 792 large parameter tensors retained paged uint8 moment allocations after restoration, the second checkpoint and Diffusers output completed, and a UNet weight changed between checkpoints. Sampled peak GPU use was 15,832 MiB; worker swap reached about 163 MiB in the stopped phase and zero was observed in the resumed phase. On the matched 2-step `1e-6` test, an exhaustive scan found 34,058,429 / 2,567,463,684 BF16 UNet values changed with 8-bit direct-weight AdamW (1.3265%) versus 43,829,230 / 2,567,463,684 with Disk AdamW fp32 masters (1.7071%); all values were finite. These are different optimizers, not an isolation of one factor or an image-quality assessment. The paired disk run took 72.1 and 87.1 seconds per step, used a sampled 6,320 MiB GPU, and had no observed worker swap.
- The cap limits this process's PyTorch allocator on a 16 GiB RTX 5080; it does not reproduce all hardware, driver, allocator or workload differences of an actual 8 GiB card. BF16 VAE and full fine-tuning remain experimental. Quality, very long runs, and other sizes/configurations remain unvalidated.

## RTX 5080 Laptop GPU: staged all-component smoke test

A 20-image local test set was cropped to SDXL buckets, captioned with the local Qwen model, and finalized; original files remained unchanged. On November 2, 2026, both full and rank-16 LoRA runs each processed two **distinct** 832×1216 images using micro batch 1, two optimizer steps, bf16 GPU forward, fp32 trainable weights and VAE, gradient checkpointing, saved-activation offload, CPU text encoders, disk-backed UNet staging, and Disk AdamW with CPU updates. Both saved a resumable checkpoint and completed Diffusers output. The full checkpoint had changed tensors in UNet, both text encoders, and VAE; LoRA checkpoints had nonzero adapters in all four components. Captions and images are private and are not in the repository.

- Full: 143.0 s and 178.1 s per step; checkpoint save 105.2 s. Sampled peak GPU memory was 15,046 / 16,303 MiB and minimum available RAM was 10,969 MiB. A one-second process monitor sampled 0 MiB worker swap; brief spikes could be missed.
- LoRA: 59.5 s and 53.2 s per step; checkpoint save 0.49 s. Sampled peak GPU memory was 15,590 / 16,303 MiB and minimum available RAM was 21,161 MiB; sampled worker swap was 0 MiB.
- For the full test, a late `/proc` process-I/O sample recorded approximately 195 GiB read and 193 GiB written, including training and checkpoint/output work up to that sample. These counters are process-level I/O, not a measurement of SSD wear; actual device writes and other configurations vary. This is a substantial cost for longer runs.

These are brief hardware smoke tests, not image-quality, reconstruction, long-run stability, or universal memory-fit validation. Other resolutions, datasets, batch/accumulation settings, software versions, and concurrent applications may behave differently. CPU/GPU arithmetic and random streams may differ across placements. VAE adaptation remains experimental.
