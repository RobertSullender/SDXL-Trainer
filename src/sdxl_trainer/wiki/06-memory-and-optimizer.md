# Memory and optimizer

## Your RTX 5080 and 32 GB RAM

SDXL is large. The fp32 UNet alone is roughly 10 GiB. Training adds gradients, optimizer state, activations, text encoders, and temporary allocations. A small micro batch reduces per-pass activations; gradient accumulation allows a larger effective batch across several such passes. Accumulation does not remove model weights or optimizer state.

Preflight reports a conservative device-memory floor and a disk estimate. Neither is a measured peak. An fp32 configuration whose estimated floor exceeds available device memory is rejected before loading; reduced-precision estimates instead produce a warning. A configuration below the estimate can still run out of memory because of activations, drivers, allocator fragmentation, and other applications.

Full training of all components on 16 GB is experimental. Without component offload, full and LoRA training with both text encoders and the VAE enabled ran out of VRAM before the first update at 1024×1024 on the tested RTX 5080 Laptop GPU, even with batch 1, bf16 forward, gradient checkpointing and saved-activation offload. This does not establish whether other settings or hardware will fit. 32 GB of RAM can also become a limit with activation offload, CPU components, or export. Close other GPU workloads and monitor both RAM and VRAM during initial validation.

## Fast memory selection

Fast defaults train the UNet with BF16 weights/forward and freeze both text encoders and the FP32 VAE. Frozen caches are prepared on GPU before trainable components are placed there, then the frozen models move off GPU. Saved activations stay on GPU by default to avoid repeated CPU transfers; gradient checkpointing remains enabled. Enable **Offload saved activations** when memory pressure justifies the transfer cost.

Complete-caption chunking remains the default, including the fast profile. Verbose captions can occupy many native CLIP windows and still increase UNet activation memory and time. Optional **native** caption context reduces conditioning to the first 75 content tokens per tokenizer without editing caption files. It is an explicit content tradeoff, not an automatic response to memory pressure.

The fast full optimizer is paged 8-bit AdamW, while fast LoRA uses ordinary AdamW with fused CUDA updates. Neither configuration guarantees a 16 GB fit. FP32 weights, Disk AdamW with FP32 moments/masters, trainable text encoders/VAE, CPU activation offload, and every component-placement option remain available.

## Component offload

Under **Training → Memory → Component offload**, choose where the trainable components run. With **Compute device** set to CUDA, the UNet is trained on the selected GPU. The text encoder choice affects both CLIP encoders together. Frozen components move off the training GPU after cache preparation; disabling preparation uses the earlier CPU encoding path.

- **No component offload** keeps selected trainable components on the GPU.
- **Text encoders on CPU** trains both encoders on CPU when selected; the trainable VAE stays on the GPU.
- **Text encoders and VAE on CPU** trains the selected encoders and VAE on CPU.
- **Text encoders on CPU; move UNet for VAE** keeps the selected encoders on CPU and temporarily parks the UNet in disk-backed CPU memory during GPU VAE work, then returns it to the GPU for UNet work and optimizer updates.
- **Text encoders on GPU; move UNet for VAE** keeps the selected encoders on the GPU and parks the UNet during GPU VAE work in the same way. This needs more VRAM for text encoders but permits CUDA optimizer updates when all trainable weights fit on one GPU.

UNet staging occurs when **Train VAE** is enabled.

Staging with VAE training requires **Disk AdamW** and `auto` or `disk` gradient storage. In this mode `auto` selects disk gradients to reduce RAM pressure. The app reserves roughly 10 GiB of additional temporary disk space for an fp32 UNet, or roughly half that for 16-bit weights; the staging file is anonymous and is released when the training worker exits. The app reuses an unchanged temporary UNet snapshot between parks and invalidates it when optimizer weights change, avoiding redundant writes without changing the training objective. The OS may also use RAM for disk pages, and cache eviction is advisory. With trainable components on both CPU and GPU, Disk AdamW uses CPU optimizer updates; explicitly selecting CUDA updates is not supported for that mixed placement. These transfers, CPU training and disk writeback can be very slow and put pressure on RAM, swap and disk. More free VRAM does not mean the system has enough RAM or disk.

Component offload retains the selected model-weight precision and the existing full-resolution VAE reconstruction, KL and latent-anchor objective. It does not use VAE tiling or reduce image resolution. CPU text encoders match the selected model precision by default; the opt-in fp32 CPU text setting below can override it. CPU and GPU calculations and random streams differ, so the result need not be bitwise identical across placements. None of these settings guarantees image quality or that every job will fit.

Watch available RAM, system swap, worker swap and GPU memory during the first run. High or steadily rising swap can make the computer unresponsive; stop a run if needed and allow time for a safe checkpoint. Monitoring displays measurements but does not automatically stop a run at a memory threshold. Keep the same component-offload selection when resuming a checkpoint; changing placement requires a new run.

## Tested 16 GB configuration

A short test on an RTX 5080 Laptop GPU used **Text encoders on CPU; move UNet for VAE**, Disk AdamW with CPU updates and disk gradients, micro batch 1, bf16 forward, and checkpointing plus saved-activation offload. With UNet, both text encoders and VAE enabled, full and LoRA runs each trained on two different 832×1216 images and saved a checkpoint and complete Diffusers output. The full run took approximately 143 and 178 seconds per step and issued about 193 GiB of process writes by a late sample; the LoRA steps took approximately 60 and 53 seconds. Device memory sampled as high as 15,046 MiB for full and 15,590 MiB for LoRA out of 16,303 MiB. Process I/O counters are not a direct measurement of SSD wear. Keep other GPU workloads closed and monitor resources; longer runs and image quality have not been validated.

An additional full BF16-weight/BF16-VAE test on the RTX 5080 used a PyTorch allocation cap of approximately 8 GiB. Two different 1216×832/832×1216 images completed, one with a 306-token caption; the two steps took roughly 203 and 464 seconds and the checkpoint saved in 100 seconds. All four components changed. Sampled GPU use reached 7,898 MiB and sampled worker swap was zero. A late process I/O sample showed roughly 213 GiB written; this is not a direct SSD-wear measurement. The same cap with an fp32 VAE ran out of GPU allocation space before the first step. This cap is a simulation on a 16 GiB RTX 5080, not validation on an actual 8 GiB card. BF16 VAE quality and longer runs require validation.

## Optimizers

**Disk AdamW** is the memory-oriented alternative to the fast defaults. During each backward pass it moves fp32 gradients from the GPU and accumulates them in system RAM or a disk-backed mapping. Its fp32 optimizer moments remain in mapped files. It applies AdamW without 8-bit state quantization and globally clips gradients before updates. Numerical tests compare updates and resumable state against ordinary torch AdamW.

**Disk AdamW gradient storage** offers `auto`, `ram`, and `disk`. Auto selects RAM only when Linux cache eviction is supported, available memory accounts for the gradient buffer and a 12 GiB reserve, and, if swap is configured, at least 2 GiB of it remains free. A container memory limit can further reduce the available memory used by this check. Otherwise auto selects disk; staged UNet and VAE training also select disk gradients when set to auto. Explicit RAM selection requires the same memory and eviction headroom and is rejected if it is unavailable; the free-swap check applies to auto.

When any trainable weights need fp32 masters, the admission check also reserves another amount equal to the fp32 gradient buffer. For a reduced-precision full SDXL UNet, that is roughly 12 GiB plus two buffers of about 9.6 GiB each: around **31 GiB of available RAM**. On a machine with 32 GB total RAM, auto will therefore usually choose disk gradients, and explicitly requesting RAM is likely to be rejected. Both text encoders or the VAE add to the requirement when trained.

At a completed optimizer boundary, the app releases a RAM-gradient buffer before saving checkpoint component copies. If training continues, it checks memory headroom again before allocating the buffer for the next backward pass; `auto` also rechecks configured swap headroom. If the check fails, training stops; resume the latest completed checkpoint with disk gradient storage. These checks and releases reduce pressure but do not guarantee a fit or prevent swap. RAM, page cache, activation offload, and other programs compete for memory, so monitor RAM and swap throughout the run.

**Disk AdamW update device**, under **Training → Optimization**, offers `auto`, `cuda`, and `cpu`. With reduced-precision trainable weights and fp32 masters, auto conservatively selects CPU updates. Explicit `cuda` streams fp32 masters and moments in bounded chunks through GPU scratch space when all trainable weights are on the same CUDA device and sufficient VRAM is available; it does not put the entire optimizer on the GPU. For fp32 trainable weights, auto may select CUDA when there is sufficient headroom, otherwise CPU. Mixed CPU/GPU trainable components cannot use explicit CUDA updates. The selected update backend is saved with checkpoints; auto preserves that backend on resume. Older checkpoints resume on their original CPU backend, and selecting a conflicting backend is rejected. CPU and GPU calculations can differ slightly in fp32 rounding, so results need not be bitwise identical between backends. Neither backend guarantees image quality.

The mappings stay open rather than synchronously flushing every tensor on every pass. Completed optimizer-moment regions are flushed in bounded batches and offered for eviction to limit page-cache pressure. When gradients are disk-backed, already-consumed gradient regions are also flushed and offered for eviction. Linux decides whether to honor this cache advice; it is not a hard memory limit and can increase disk writes. Linux may keep other pages in its RAM page cache and reclaim file-backed pages under pressure. Monitor RAM and swap because pressure can still slow training. Optimizer moment files are explicitly flushed and synchronized when saving a checkpoint. A power loss can still lose work since the last completed checkpoint.

An SSD with substantial free space is appropriate. Full-model runs can need hundreds of gigabytes for gradients, moments, checkpoints, and output. With all components and two retained checkpoints, the conservative estimate is around 176 GiB. Keeping one checkpoint reduces the estimate. Do not place optimizer state on a small RAM filesystem. Disk failure or lack of space can interrupt a run.

**Paged AdamW · 8-bit moments (direct weights)** is selected by fast full-training defaults under **Training → Optimization**. Paged AdamW stores large optimizer moments in quantized form, with small tensors typically retaining fp32 state. It updates live model weights directly and does not supply fp32 master weights for full bf16/fp16 training. Quantized moments alter optimizer arithmetic, and reduced-precision gradients can round or underflow during unscaling and clipping; small weight updates can also round away. LoRA adapters remain fp32. These differences can affect results; compare output quality rather than assuming equivalence to Disk AdamW. See the [bitsandbytes optimizer documentation](https://huggingface.co/docs/bitsandbytes/main/optimizers).

This option requires CUDA and all **trainable** components on one GPU. CPU-offloaded trainable text encoders or VAE and staged UNet/VAE training are unsupported. Frozen components can remain on CPU. Paged optimizer state can move between GPU and system RAM through CUDA unified memory, but live weights and accumulated gradients still occupy GPU memory. Paging can increase RAM, swap and transfer time and does not guarantee a run fits; monitor VRAM, RAM and swap. See the [bitsandbytes paging explanation](https://huggingface.co/docs/bitsandbytes/explanations/optimizers).

The integration currently accepts local **bitsandbytes 0.49.2**. When the remaining configuration is valid, runtime preflight performs a small native CUDA optimizer probe before model loading. The local CUDA 13.2 PyTorch runtime's installed bitsandbytes package lacks a matching CUDA 13.2 binary; with this installation, the explicit **8-bit CUDA binary override** `130` is required and passed the probe using its installed CUDA 13.0 binary. This is an experimental override, not a general compatibility guarantee. An empty override requests the PyTorch CUDA version. Use a compatible local binary and rerun the probe; [upstream installation requirements](https://huggingface.co/docs/bitsandbytes/installation) describe supported platforms. Paged checkpoints record the bitsandbytes and PyTorch versions, PyTorch CUDA version, override, and GPU capability; resume requires the same recorded runtime identity. A successful probe or short run does not guarantee training quality, memory fit, or long-run stability.

On the RTX 5080 Laptop GPU, a short full UNet-only bf16 test used two different 832×1216 images and learning rate `1e-6`. Paged 8-bit AdamW took 16.0 and 16.4 seconds per step, reached 15,832 MiB sampled GPU use, and saved a checkpoint and Diffusers output. A repeat sampled about 2.2 GiB worker swap during saving. The paired fp32-master Disk AdamW test took 72.1 and 87.1 seconds per step, reached 6,320 MiB sampled GPU use, and had no worker swap observed. A stopped 8-bit run also resumed for its second step and completed. Samples can miss brief peaks, and these figures do not guarantee performance or fit for another run.

After two steps, approximately 1.33% of the bf16 UNet values differed from the source with paged 8-bit AdamW, versus 1.71% with Disk AdamW; all scanned values were finite. The methods differ in more than one way. These percentages are not a measure of output quality or long-run stability, and neither optimizer is established as better by this comparison.

**AdamW** keeps ordinary optimizer state in memory and is the fast LoRA choice. **Fused GPU AdamW** combines update operations in CUDA kernels when all trainable weights share one GPU. CPU or mixed placement uses ordinary AdamW; the switch is ignored by Disk AdamW, paged AdamW, and SGD. Fused arithmetic can differ slightly from the earlier unfused path. LoRA adapters remain FP32 with a BF16 frozen backbone. Ordinary AdamW can require too much memory for full training. **SGD** uses a different optimization method; choosing it changes training behavior and is not a quality-equivalent substitute for AdamW.

## Frozen caches

**Prepare frozen caches before training** encodes images and text on GPU before trainable components occupy it. CPU training prepares them on CPU. After preparation, frozen models move off the training GPU and steps can use cached tensors directly. Disabling preparation retains lazy CPU encoding on the first uncached visit. A trainable text encoder or VAE bypasses its corresponding frozen cache.

**Frozen VAE cache sampling** offers two behaviors:

- **sample**, the fast default, stores one deterministic sampled latent per image and reuses it on every visit. The sample depends on the run seed and cache identity, and does not consume the optimizer loop's random stream. This reduces repeated sampling work and matches the fixed-latent approach used by many trainers, but changes training randomness.
- **posterior** stores the FP32 posterior mean and log-variance and draws fresh latent noise on every visit. It requires FP32 VAE computation and retains the previous sampling behavior.

Image pixels and stored captions are unchanged by either mode. Sample caching checks finite outputs at the selected VAE precision; it cannot make an unstable FP16 VAE reliable. Cache identity separates model, image, sampling seed/mode, text-context policy, and relevant precision/preparation choices. Invalid cache entries report an error rather than silently training with mismatched data. Numerical changes require a new run; old recipes retain their original behavior when loaded for resume.

The **Frozen text cache RAM limit (MiB)** defaults to **4096**, and **Frozen VAE cache RAM limit (MiB)** defaults to **1024**. These are bounds, not startup allocations: memory grows only as entries are used. Entries beyond a budget remain in validated local files and may be read again. Set either limit to zero to disable that RAM layer while keeping the disk cache. Caches use CPU RAM, not persistent GPU memory; system RAM is also needed by model loading, the UI, offloaded activations, other programs, and checkpoint export. Use smaller budgets when needed.

**Show phase timings** and **Monitor NVIDIA GPU** can be switched independently under the training controls. The monitor samples device-wide utilization and VRAM, so other applications and short bursts affect the readings. It also samples host-wide available RAM and swap usage and the training worker's swap when available; system swap includes all processes. High swap use can slow training severely. Phase wall times and GPU stream intervals can overlap and are not exclusive active-compute timings. Profiling synchronizes the GPU once per optimizer step and may add overhead. Checkpoint time is reported separately from the completed step.

## Precision

**UNet and text weight precision** selects fp32, bf16, or fp16 model weights. BF16 is the fast default; FP32 retains the original Disk AdamW path when that optimizer is selected. For full training of 16-bit parameters, Disk AdamW stores authoritative fp32 master weights and fp32 moments on disk, accumulates fp32 gradients, and rounds updated weights to the selected model precision. This saves model VRAM but needs additional disk space; updates default to CPU and can optionally use CUDA under the conditions above. Masters cannot recover precision lost when loading or computing with 16-bit weights. LoRA adapters stay fp32. The separate paged optimizer uses 8-bit moments and does not provide these fp32 masters.

**Trainable CPU text precision** defaults to `match`, so both CLIP encoders use the selected model weight precision. Choose `fp32` to load and run both trainable CPU text encoders in fp32 even when the UNet uses bf16 or fp16. Enable **Train both text encoders** and either select CPU text component offload with CUDA training or choose CPU as the compute device. The option is available for full and LoRA training. It can add roughly 1.5 GiB of system RAM compared with 16-bit text weights; monitor RAM and swap. Speed and fit depend on the machine and are not guaranteed.

FP32 CPU text encoding uses the selected source variant: casting already-rounded fp16 or bf16 source files to fp32 cannot recover their lost bits. FP32 text embeddings and pooled conditioning reach the UNet in fp32; the UNet uses its selected autocast precision, so its input and time-conditioning numerics can differ from `match`. This changes training behavior and does not guarantee output quality. Keep the same CPU text precision when resuming; to change it, start a new run.

**Forward precision** controls autocast independently for fp32-weight models. BF16 or FP16 weights require the matching forward setting. FP16 uses dynamic loss scaling: gradients are unscaled before clipping and an overflowing batch is retried with a smaller scale. The scaler state is included in checkpoints. Reduced-precision CPU text backward can use a slower native backend; selecting fp32 CPU text explicitly disables CPU autocast for those text encoders.

**Allow TF32 acceleration** enables NVIDIA matmul and cuDNN TF32 paths when forward precision is BF16 or FP16. It is enabled by fast defaults and can change results for operations that otherwise use FP32 arithmetic. Under the new explicit policy, FP32 forward disables TF32 regardless of the checkbox. The worker restores its earlier backend settings when it exits; this choice does not alter caption generation.

Older recipes and checkpoints automatically retain the legacy backend policy—TF32 disabled for matmul and enabled for cuDNN—rather than adopting the new explicit checkbox policy; new explicit FP32-forward runs disable both TF32 paths.

**VAE weight and compute precision** defaults to fp32. BF16 and FP16 are explicit experiments. The original SDXL VAE is designed to be upcast for stability and fp16 may overflow or produce non-finite values. A source fp16 or bf16 variant is already rounded; upcasting it cannot reconstruct lost precision. The chosen Diffusers file variant applies to the VAE as well as the UNet and text encoders; selecting fp32 VAE computation does not independently select an fp32 VAE file. Assess VAE reconstructions and generated samples before relying on a lower-precision VAE.

Under **Training → Files → Diffusers file variant**, select `default`, `fp16`, or `bf16` to match the local component filenames. The model library offers an official SDXL fp16 preset; the exact variant must exist for all four components. Loading a variant does not itself select weight or forward precision. App-generated Diffusers outputs use canonical filenames: select the `default` file variant when using one as a new base, regardless of its tensor dtypes. Reducing weight precision, device placement, and CPU/GPU kernels can change numerical results. A short successful run is not a quality or 8 GB VRAM guarantee.

## If a run does not fit

Use micro batch 1, gradient checkpointing, disk AdamW, and activation offload. Disable training components that are unnecessary for your experiment. CPU mode remains an option at a major speed cost. Keep the native bucket resolution unless you deliberately redesign and validate the dataset pipeline; this version does not silently lower resolution to make a job fit.



## Checkpoint RAM headroom

Before saving a resumable checkpoint, the worker releases disposable CPU RAM copies of frozen text and VAE cache entries. Their validated disk files remain intact. Later training steps reload entries without repeating encoding or changing fixed latent samples; this makes room for checkpoint and final-output serialization. Actual system RAM reclamation depends on the allocator and operating system.
